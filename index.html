    Case study: from zigzag errands to a smarter route

    Smart Multi-Stop Planner
    Single-file web appVanilla JS + SVGDemo data, no live maps

    The problem I ran into

    Planning a day of errands, I listed stops in whatever order I remembered them. The route then criss-crossed town, passing the same junctions again and again. The pain was never one long leg. It was many avoidable ones. A zigzag version of that trip is still the demo loaded when you open the app.

    The insight

    The order of stops is the biggest lever, but a shorter order is only useful if it respects real life: a must-do stop, fixed visit times and a limited day.

    How I iterated

    Find the shortest orderTried every possible order for small trips and compared the best one with the order entered. A clear before-and-after was enough to prove the idea.
    Add real-life constraintsAdded priorities (Must Visit, Important, Flexible), visit durations, lock-a-stop-at-position and an available-time limit. When a day is too long, Flexible stops are dropped first, then Important ones. Must Visit and locked stops are never dropped, and the app says what was left out and how much time that frees.
    Handle bigger tripsTrying every order stops being practical as stops grow. Above 8 stops the planner builds a nearest-neighbour route, then improves it with 2-opt reversals and stop moves. The result is labelled “best found”, not “guaranteed shortest”.
    Make it trustworthyAdded a map animation showing your original order against the orders tried. Added an original-versus-optimised table, a “why this order” explanation, scattered-trip warnings and a plain “demo estimates” notice.
    Polish and exploreAdded a logo, summary tiles, clearer notes, and demo places that preview live on the map. The demo now uses a fixed 12-point coordinate dataset (a start plus stops A–K) with a closed tour that returns to the start.

    What I built

    • Setup panel: places, start and end, priorities, visit times, travel mode, departure, time available and optimisation goal.
    • Interactive map: pan, zoom, direction arrows, and click-to-add places.
    • Results panel: savings, a timed itinerary, conflict guidance and a shareable summary.

    Decisions and trade-offs

    • Fictional town: keeps the product runnable anywhere with no keys or live data. Distances are Euclidean on schematic coordinates at fixed speeds and are always labelled as estimates.
    • Separate engine: the planner works from a distance and duration matrix, so real routing data could replace the demo matrix without rewriting the logic.
    • Honest wording: the app says when a result is a best guess, and explains drops and conflicts instead of failing silently.

    Product documentation

    • Algorithm: a nearest-neighbour route is improved with 2-opt reversals and single-stop moves. It also starts from your entered order if that is better, so the result is never worse than the original. Locks and priorities are respected.
    • Assumptions: positions are schematic map units (0–100), 1 unit = 50 m. Distance is Euclidean. Time uses fixed speeds (drive 28, cycle 14, walk 4.8 km/h). Cost is distance × your per-km rate. Visit time is tracked separately from travel time.
    • Success metrics: distance saved and % reduction, travel time saved, estimated cost saved, and every stop visited exactly once with a return to the start. All are calculated from the actual sequences.
    • Limitations: not real roads, GPS or traffic. With more than 8 stops the result is the best order found, not a proven optimum. Costs exclude tolls, parking and fuel changes.
